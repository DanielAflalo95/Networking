# OSPF Troubleshooting Lab

## Task Overview

In this lab, the network was already mostly configured, and the goal was to troubleshoot several OSPF and routing problems.

The main focus was:

- Adding a new serial OSPF connection
- Fixing an incorrect OSPF network type
- Troubleshooting OSPF neighbor formation
- Fixing default route advertisement
- Examining the OSPF LSDB

---

## 1. Configuring the New R1–R2 Serial Link

The serial connection between R1 and R2 was newly added.

R1 was the **DCE side**, so I configured the required clock rate on R1:

**interface Serial0/0/0**  
**clock rate 128000**

On both R1 and R2, I enabled OSPF directly on the serial interfaces:

**ip ospf 1 area 0**

I also made sure the interfaces were enabled with:

**no shutdown**

After the configuration, R1 and R2 successfully formed an OSPF neighbor relationship.

---

## 2. Fixing the Missing `10.0.2.0/24` Route

The problem was on **R3 GigabitEthernet0/1**.

That interface was configured with the wrong OSPF network type:

**ip ospf network point-to-point**

Since G0/1 is an Ethernet interface, the correct behavior should be the default **Broadcast** network type.

I removed the incorrect configuration:

**interface GigabitEthernet0/1**  
**no ip ospf network point-to-point**

After removing it, the interface returned to the default Broadcast network type and the `10.0.2.0/24` network was advertised correctly.

---

## 3. Fixing the OSPF Neighbor Problem with R5

R2 and R4 were unable to become OSPF neighbors with R5.

The problem was an **OSPF Hello/Dead timer mismatch**.

R5 had manually configured timers:

- Hello Timer → `5`
- Dead Timer → `20`

OSPF neighbors must use matching Hello and Dead intervals.

To remove the custom settings and return to the default values, I used:

**interface GigabitEthernet0/0**  
**no ip ospf hello-interval 5**  
**no ip ospf dead-interval 20**

After removing the manual timer settings, R5 matched the other routers and the OSPF adjacencies formed successfully.

---

## 4. Fixing External Connectivity

PC1 and PC2 could not reach the external server `8.8.8.8`.

R5 already had:

**default-information originate**

configured under OSPF.

However, R5 itself did not have a default route in its routing table.

I added a static default route toward ISP1:

**ip route 0.0.0.0 0.0.0.0 203.0.113.2**

R5 could then advertise the default route into the OSPF domain.

The internal routers learned:

`O*E2 0.0.0.0/0`

and PC1/PC2 were able to reach the external network.

---

## 5. Examining the OSPF LSDB

I checked the Link-State Database using:

**show ip ospf database**

The important LSAs present included:

- **Type 1 – Router LSA**  
  Generated by every OSPF router to describe its own links.

- **Type 2 – Network LSA**  
  Generated by the DR on the shared Ethernet segment.

- **Type 5 – AS External LSA**  
  Generated by R5 as the ASBR to advertise the external default route.

## What I Learned

This lab focused mainly on **OSPF troubleshooting**.

I practiced identifying common OSPF problems such as:

- Incorrect OSPF network type
- Hello/Dead timer mismatches
- Missing default routes
- Understanding that **default-information originate** normally requires an existing default route

I also reinforced how **Type 1, Type 2, and Type 5 LSAs** appear in the LSDB and how they relate to routers, shared networks, and external routes.
